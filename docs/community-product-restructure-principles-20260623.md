# よりそい つながる プロダクト再整理メモ

作成日: 2026-06-23
対象: `medicanvas/yorisoi-tsunagaru`

## このメモの目的

これまでの改善は、主にデザイン・見た目・UIの方向性を整える作業だった。

一方で、機能、画面、オンボーディング、設定、投稿体験には、以前の「お隣さん探し」「マッチング」「記録アプリ」寄りの設計がまだ残っている。

ここからは、見た目だけではなく、プロダクトとしての体験を整理し直す。

このメモは、今後の実装前に戻るための判断基準として残す。

病名・症状・不安・部屋を固定リストから解放するための詳細なデータ設計は、`community-topic-data-design-20260623.md` に分けて残す。

## プロダクトの中心

よりそい つながるは、一般的なSNSではない。

目指す中心は次の通り。

> 病気・症状・診断前の不安を抱える人が、登録前でも近い体験談を読み、必要な時だけそっと声を置ける場所。

大事にすること:

- 登録前でも読める。
- 書くことを急がせない。
- 医療判断をしない。
- 病気の重さやつらさを比べない。
- 投稿者の影響力や人気ではなく、「近い声」を中心にする。
- 体験談や投稿は、競争や拡散ではなく、安心して読める声として扱う。
- 病名が確定していない人、相談相手がいない人も入れる。

## 中心機能

中心機能は4つに絞る。

### 1. 読む

登録前でも、同じような人の体験談を読める。

対象:

- `/home`
- `/rooms/[id]`
- `/voice/[id]`

役割:

- まず安心する。
- 自分だけではないと感じる。
- まだ書けない人も参加できる。

### 2. 探す

病気、症状、暮らしの悩みから近い声を探す。

対象:

- `/find`
- `/rooms`

役割:

- 病名がある人は病名から探せる。
- 病名がない人は症状や不安から探せる。
- 難病・希少疾患・がん・慢性疾患・診断前の不安まで広げられる。

### 3. 部屋に入る

同じ病気、症状、悩みの声をまとめて読める。

対象:

- `/rooms`
- `/rooms/[id]`

役割:

- 全体タイムラインよりも近い声を読む。
- 「入らなくても読める」安心感を残す。
- 入ることで保存・反応・投稿しやすくする。

### 4. 書く

SNS投稿ではなく、「声を置く」体験にする。

対象:

- `/post`
- `/post/condition`
- `/post/star`

役割:

- 気持ちを整理する。
- 同じような人に体験を残す。
- まだ誰にも見せたくないものは自分だけに置く。

## 「書く」の再定義

今後の投稿体験では、「書く」を1種類にしない。

| 種類 | 意味 | 主な公開範囲 |
|---|---|---|
| ひとこと吐き出す | いまの気持ちを短く置く | 全体 / 部屋 / 自分だけ |
| 体験談を書く | 同じ人の参考になる経験を残す | 全体 / 部屋 |
| 聞いてみる | 同じような人に質問する | 部屋 |
| 自分だけメモ | まだ誰にも見せない | 自分だけ |

重要:

- 「投稿する」よりも「そっと置く」「声を置く」の方がブランドに合う。
- 書く前に、公開範囲を分かりやすくする。
- AIの「やさしく整える」は、医療判断や正解提示に見えない制約が必要。
- 何も書けない人も、読むだけで成立するようにする。

## オンボーディングの見直し方針

現状のオンボーディングには、以前の「お隣さん探し」「マッチング」寄りの名残がある。

特に見直したい要素:

- 同じ生活リズムの人とつながりたい
- 考え方が近い人と話したい
- 相談に乗りたい
- 性格・暮らしのリズム
- 性別・生年月日の強い入力

新しいオンボーディングは、短く、安心して始められるものにする。

### 推奨する新構成

1. ようこそ
   - 読むだけでも大丈夫。
   - 書くのはあとでよい。

2. 気になること
   - 病気名
   - 症状
   - 診断前
   - 暮らしの悩み

3. 使い方
   - まず読む
   - 近い部屋を探す
   - いつか書く

4. ニックネーム
   - 本名不要
   - アバター選択
   - 個人情報は最小限

### 個人情報の扱い

現状の「性別・生年月日は変更不可、答えたくないを出さない」は、今のプロダクトには強すぎる。

理由:

- 安心して入る場所なのに、最初に個人情報を強く求めると離脱しやすい。
- 病気や不安を抱えている人には、最初の入力負荷が大きい。
- 公開コミュニティの価値は、まず読むことにある。

方針:

- 性別は任意にする。
- 生年月日ではなく、必要なら年代程度にする。
- 本当に必要な情報は、利用が進んだ後に聞く。

## 病気・症状・不安・部屋の再設計

現状は、病気候補、症状候補、不安候補、部屋、投稿タグがかなり固定的に結びついている。

詳細なデータモデル、検索UX、自由入力病名、診断前、部屋案内の扱いは、`community-topic-data-design-20260623.md` を正本とする。

これはデモでは分かりやすいが、本番の患者さん向けには弱い。

理由:

- 患者さんが自分の病名を見つけられないと、最初の時点で「自分の場所ではない」と感じる。
- 難病・希少疾患・がん・診断前の不安まで対象にするなら、画面上の固定リストだけでは足りない。
- メディキャンバス側としても、実際にどんな病気の方が使っているかをデータとして把握したい。
- 一方で、病気ごとに専用テンプレートや専用画面を作ると運用が重くなる。

したがって、病気名とアプリ側のテンプレートを分ける。

### 基本方針

病気は「選べる」だけでなく、「入力して始められる」ようにする。

画面上は次の順にする。

1. 画面上部に「病名を入力して探す」を置く。
2. よく選ばれる病気を先に出す。
3. リストにない病気も自由入力で始められる。
4. 「まだ診断名が決まっていない」も選べる。
5. 裏側では、患者さんが入力した病名と、アプリで使うテンプレートを分けて保存する。

### 画面上の出し方

病気選択画面では、スクロールして探させるのではなく、まず検索できるようにする。

例:

```text
病名を入力して探す
[ ベーチェット病                  ]

よく選ばれる病気
潰瘍性大腸炎 / クローン病 / 関節リウマチ / SLE / 1型糖尿病

診断名がまだ決まっていない
検査中・疑い病名・診療科だけ分かっている方はこちら
```

検索結果に完全一致がない場合:

```text
「ベーチェット病」で始める
```

この導線が重要。

### 裏側の保存形式

病気名そのものと、アプリ側で使う表示・記録テンプレートを分ける。

例:

```json
{
  "selectedDiseaseName": "ベーチェット病",
  "selectedDiseaseId": null,
  "selectionMethod": "free_text",
  "templateKey": "general",
  "diagnosisStatus": "diagnosed"
}
```

候補から選んだ場合:

```json
{
  "selectedDiseaseName": "潰瘍性大腸炎",
  "selectedDiseaseId": "uc",
  "selectionMethod": "catalog",
  "templateKey": "ibd",
  "diagnosisStatus": "diagnosed"
}
```

診断名がまだ決まっていない場合:

```json
{
  "selectedDiseaseName": null,
  "selectedDiseaseId": "diagnosis_pending",
  "selectionMethod": "status",
  "templateKey": "general",
  "diagnosisStatus": "pending"
}
```

### テンプレートの考え方

テンプレートは、画面や質問内容を変えるための内部分類。

病名そのものとは別にする。

| templateKey | 用途 |
|---|---|
| `general` | 多くの病気・診断前・自由入力病名に使う標準テンプレート |
| `ibd` | IBD向け。腹痛、便、食事、通院不安などを少し厚めに扱う |
| `cancer` | がん向け。治療選択、仕事、家族への伝え方などを扱う |
| `autoimmune` | 膠原病・自己免疫疾患向け。疲れ、痛み、日差し、見た目に出ない症状など |
| `neurology` | 神経難病向け。しびれ、震え、外出、介助、進行不安など |

最初から全部を作り込まない。

本番初期は、ほとんどを `general` で受け止めてよい。

重要なのは、患者さんが入力した病名を失わないこと。

### 部屋との関係

病気を選んだら、必ず専用部屋を作る必要はない。

たとえば「ベーチェット病」と入力された場合:

- 既に `ベーチェット病` の部屋があれば、その部屋へ案内する。
- なければ、`診断名・病名について話す部屋` や `症状・不安の近い部屋` に案内する。
- 裏側では `selectedDiseaseName = ベーチェット病` として保存する。

つまり、病気名と部屋は1対1でなくてよい。

部屋は次の3種類に分ける。

| 部屋の種類 | 例 | 役割 |
|---|---|---|
| 病名部屋 | 潰瘍性大腸炎、クローン病、SLE | 参加者が多い病気の近い声を読む |
| 症状部屋 | 腹痛、強い疲れ、眠れない夜 | 病名がなくても入れる |
| 不安・暮らし部屋 | 診断前、仕事との両立、家族に話す | 病名に関係なく共通する悩みを扱う |

### 症状・不安の扱い

症状や不安も固定リストだけにしない。

ただし、病気名ほど自由入力を前面に出しすぎると、整理が難しくなる。

推奨:

- 初期表示はよくある症状・不安を出す。
- 検索できる。
- 見つからない場合は「この言葉で探す」または「自由に書く」を出す。
- 投稿やオンボーディングで入力された言葉は、裏側でそのまま保持する。

### 現行実装で変えるべき点

現状:

- `lib/mock/explore.ts` の `conditions` / `symptoms` / `concerns` が画面候補と部屋リンクを同時に持っている。
- `lib/mock/rooms.ts` の部屋が固定で増えている。
- `lib/onboarding/types.ts` の `CONDITION_CATALOG` がオンボーディング専用の小さな候補になっている。

今後:

- `disease catalog` と `room catalog` を分ける。
- `selectedDiseaseName` と `templateKey` を分けて保存する。
- `roomHref` は必須にしない。
- 自由入力病名は `general` テンプレートで受け止める。
- 診断前は病名ではなく `diagnosisStatus = pending` として扱う。

### 実装前の判断

次に実装する前に決めること:

- 病名自由入力をオンボーディングで聞くか、`/find` で先に使わせるか。
- 「まだ診断名が決まっていない」を病気候補の中に置くか、別カードにするか。
- 自由入力された病名で、すぐ部屋を作るように見せるか、近い部屋へ案内するか。
- メディキャンバス側で集計したい項目をどこまで保存するか。
- 将来の正式な病名マスターを、難病情報センター、がん種、ICD等とどう接続するか。

特に見直したい要素:

- 診察の記録
- 病気を見つめなおす
- お隣さん
- 性格・暮らしのリズム

設定は、次の5つに絞る。

## デザイン統合の考え方

現在は、画面ごとにデザインの思想が分かれている。

### 新しい正本UIに近い画面

- `/home`
- `/find`

特徴:

- 登録前でも読める。
- 余白があり、静か。
- 病気・症状・悩みをやさしく探せる。
- SNSらしさはあるが、競争感が強くない。

### 古いUIの名残が強い画面

- オンボーディング
- 設定
- マイページ
- 一部の投稿/通知画面

特徴:

- 以前の「お隣さん」「記録」「マッチング」の言葉が残る。
- 新しい公開コミュニティの価値とずれる箇所がある。
- デザインの密度や言葉づかいが正本UIと違う。

## 画面整理の判断軸

次にやるべきことは、全画面を次の4分類に分けること。

| 分類 | 意味 |
|---|---|
| 残す | 今の方向で磨く |
| 作り直す | 役割は必要だが、今の設計が違う |
| 隠す | 今は不要だが将来使うかもしれない |
| 削る候補 | コミュニティ版には不要 |

この分類を決めてから、実装に入る。

## 次にやること

次回以降は、この順番で進める。

1. 画面ごとに「残す / 作り直す / 隠す / 削る候補」を確定する。
2. オンボーディングを、新しいプロダクト思想に合わせて再設計する。
3. 設定画面を、安心・公開範囲・通知・データ・ヘルプに絞り直す。
4. 「書く」体験を、ひとこと / 体験談 / 聞いてみる / 自分だけメモに分ける。
5. 正本UIのブランドトーンを、部屋・投稿・登録・オンボーディング・設定に展開する。
6. 最後に実装へ入る。
